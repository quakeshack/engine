# Client Entities

Quake draws its world from two kinds of things: edicts the server simulates and mirrors to every client, and a handful of hard-coded client-side effects (particles, beams, dynamic lights). Anything that only has to look right, such as gibs, air bubbles, shell casings or debris, had to be a full server edict anyway, simulated by the server and sent to every client every frame.

QuakeShack lets a game create **client-only entities**: cosmetic things that exist on the client alone, move under their own physics, expire on their own, and still survive a save game. The server sends one small event (or nothing at all) instead of an edict and its per-frame updates.

This document describes what a game module can rely on. The reasoning behind it, and a log of how it was built, is in [plans/client-entity-architecture.md](../plans/client-entity-architecture.md).

A word on names: an **edict** is the engine's record of an entity (`ServerEdict` on the server, `ClientEdict` on the client): number, model, origin, links. An **entity** is what a game thinks of as the thing: on the server a `BaseEntity` attached to its edict, on the client the handler that drives its `ClientEdict`. APIs such as `SpawnClientEntity()` say "entity" because that is what the game asks for, and hand back the `ClientEdict`.

## Compared to WinQuake

| | WinQuake | QuakeShack |
| - | - | - |
| Cosmetic debris (gibs, bubbles, casings) | Server edicts: a slot, physics and network updates on the server for every piece | Client-only entities: the server broadcasts an event, each client simulates its own pieces |
| `svc_spawnstatic` decorations | Frozen forever after signon | Same, but they can run a handler, e.g. a map entity that keeps releasing effects on its own |
| Per-entity client behavior | None, the renderer reads the entity state | A handler per classname (`spawn`/`emit`/`think`) |
| Client-side gravity and collision | None, only particles fly (through walls) | A move type on the entity and the engine simulates it, and gravity particles bounce off or die on the world |
| Multi-frame effect sequencing | Hand-rolled counters | `ClientAnimationSequence` |
| Client effects and save games | Lost on load | Client-only entities and particles are part of the save |
| Hidden effect sources | Always run | Can ask whether the player could see them (`IsInPVS`) |

## The three kinds of `ClientEdict`

Everything the client draws is a `ClientEdict` (`source/engine/client/ClientEntities.ts`). It serves three lifecycles:

| Kind | `num` | Comes from | Saved | Lives in |
| - | - | - | - | - |
| Server-mirrored | `>= 0` | Entity updates over the network, interpolated between snapshots | No, the server restores them | `ClientEntities.entities` |
| Static | `-1` | `svc_spawnstatic` (the server calls `makeStatic()`), regenerated by the signon on every (re)connect | No, there is nothing to restore | `ClientEntities.static_entities` |
| Client-only simulated | `-1` | The game, through `ClientEngineAPI.SpawnClientEntity()` | Yes (`persistent`) | `ClientEntities.static_entities` |

`ClientEdict.isClientOwned()` is true for the last two. The array name `static_entities` is historical; it holds both.

## Handlers

Behavior lives in a `BaseClientEdictHandler` subclass (`source/shared/ClientEdict.ts`). The engine asks the game module for the handler of a classname through `ClientGameAPI.GetClientEdictHandler(classname)` when an entity gets its classname, and falls back to a default handler (procedural effects from model and effect flags) when the game returns `null`.

| Method | Called | Use it for |
| - | - | - |
| `spawn(parameters?)` | Once, when the entity is spawned. `parameters` is what the spawner passed to `ClientEdict.spawn()`. | Setting up state, rolling random values |
| `think()` | Every frame, for every entity that is not free, **whether or not it is visible**. The engine's physics step has already run. | Timers, expiry, own movement of a floating thing |
| `emit()` | Every frame the entity is visible and drawn | Dynamic lights, trails, particles |
| `impact(trace)` | The engine-driven physics hit the world | A bounce sound, a decal |
| `rest()` | The engine-driven physics came to rest | Switching to a resting state, a settle sound |
| `remove()` | You call it | Ends the entity: stops thinking, emitting and drawing, and frees the slot |
| `serialize()` / `deserialize(data)` | On save and load, for persistent entities | Extra state of the handler |

`think()` runs for hidden entities too, so keep it cheap, and prefer a timer over per-frame work. An entity with `EF_NODRAW` is never emitted.

## Spawning one

```typescript
const gib = engine.SpawnClientEntity('my_gib');   // persistent by default

gib.model = engine.ModForName('progs/gib1.mdl');  // must be precached by the server
gib.angles.clear();                               // a fresh entity has Infinity angles
gib.velocity.set(velocity);
gib.setOrigin(origin);                            // links it into the world, needs the model
gib.spawn({ delay: 0.5 });                        // optional parameters for the handler
```

- **Set the model before `setOrigin()`.** Linking an entity into the BSP needs its bounds.
- **Always move an entity with `setOrigin()`**, never by writing `origin`. It recomputes the BSP leafs the PVS culling relies on.
- **Models have to be precached by the server**, otherwise they are not in the client's model list. A handler declares them in `static _precache(engineAPI)`, and the game's handler registry calls that for every handler when the server precaches its resources, the way `BaseEntity._precache()` works for server entities.
- `SpawnClientEntity(classname, { persistent: false })` is for entities something else regenerates on every connect. Almost everything wants the default.

### Triggering it from the server

The server does not spawn client-only entities directly. It sends a client event (see [Game Module Contract](game-module-contract.md)), the game's client code subscribes to it and spawns the entity. One event per burst, not one per piece, keeps the traffic small. Treat the event as best effort: a lost one costs a bit of decoration.

### Map entities that become client entities

A server entity can turn itself into a static client entity by calling `makeStatic()` in its `spawn()`. The server edict is freed, the client gets an entity with the same classname, and its handler can keep producing effects on its own, with no network traffic afterwards. `makeStatic()` needs a model, so a pure effect source uses a small model with `EF_NODRAW`.

## Building blocks

All of these are opt-in. A handler composes what it needs.

### Physics: declare a move type, the engine simulates

Game code is a **user** of physics, not a provider. A handler says how its entity should move and the engine does the rest, so the game never integrates gravity, traces the world or decides when something has come to rest. That keeps the simulation in one place, which is also where a more capable physics backend can replace it later without touching any game code.

```typescript
override spawn(): void {
  this.clientEdict.movetype = moveType.MOVETYPE_BOUNCE;
  this.clientEdict.avelocity.setTo(120, 300, 40);   // tumble, degrees per second
}

override impact(trace: GameTrace): void {
  // hit the world: a bounce sound, a decal ...
}

override rest(): void {
  // came to rest on the floor
}
```

| `ClientEdict` field | Meaning |
| - | - |
| `movetype` | `MOVETYPE_NONE` (the default, the engine does not move it), `MOVETYPE_TOSS` (gravity, slides along what it hits) or `MOVETYPE_BOUNCE` (gravity, bounces off what it hits) |
| `avelocity` | Tumble rate in degrees per second |
| `gravity` | Multiplier of the world gravity for this entity, `1.0` by default |
| `onGround` | Set by the engine once the entity came to rest. A resting entity is not stepped again |

Every frame, before the handlers' `think()`, the engine steps each client-owned entity that is tossed or bouncing and not at rest. It applies the world gravity (synced from the server, so a game that changes gravity changes its client entities too), integrates the tumble, traces the static world, clips the velocity against what it hit with the formula the server uses for toss and bounce (`PhysicsMath.clipVelocity`), and moves the entity through `setOrigin()` so its BSP leafs stay right. A bounce comes to rest on a floor-like plane once it bounces up slower than 60 units per second, the same rule `ServerPhysics.physicsToss()` applies, and an entity stuck inside solid counts as at rest. Nothing is stepped while the game is paused.

Entities mirrored from the server are never stepped, whatever their fields say.

What stays with the game: choosing the move type, the launch velocity and tumble, and what an impact or the rest means. Not everything fits a move type yet: a thing that floats, like a bubble, moves itself in `think()` and checks the world only a few times per second, since a world trace per bubble per frame would add up.

### Sequences: `ClientAnimationSequence`

A client-side analog of the server's state machine, for a triggered effect with several steps. States are keyed by a typed string union and carry a model frame, a duration, the next state and an optional callback that fires once on entering (the initial state's on the first `tick()`).

```typescript
#sequence = new ClientAnimationSequence(this.clientEdict, {
  flash: { keyframe: 0, duration: 0.1, next: 'smoke', onEnter: () => this.#spawnLight() },
  smoke: { keyframe: 1, duration: 0.4, next: 'fade' },
  fade:  { keyframe: 2, duration: 0.3, next: null },     // terminal
}, 'flash');

override think(): void {
  this.#sequence.tick(this.engine.CL.time);
}
```

`setState()` jumps to a state without firing `onEnter`, so resuming from a save does not replay a sound that already played. Frames are plain indices, client models have no frame-name table.

### Knowing whether it can be seen: `IsInPVS`

`ClientEngineAPI.IsInPVS(entity)` tells whether the entity is in the PVS of the current view, also for entities that are not drawn. An effect source can skip its work while nobody can see it. It reflects the previous frame, is coarse (a wall in the way does not count), and answers "yes" when it cannot tell. If the source skips effects while hidden, replay what it missed when it comes back, so the effect does not start from nothing in front of the player.

### Other client API a handler can use

`CL.time`, `CL.frametime` and `CL.gravity` for timing and physics, `Traceline()` for the world, `DetermineStaticWorldContents()` for water and the like, `AllocDlight()` for dynamic lights, `RocketTrail()` for trails.

## Save games

Particles were always saved. Persistent client-only entities are saved the same way, so a gib in the air when the game is saved is still in the air after the load. Static entities are not saved, the signon recreates them.

For each persistent entity the engine stores its classname, model name, origin, angles, velocity and physics state (`movetype`, `avelocity`, `gravity`, `onGround`), plus whatever the handler's `serialize()` returns. A handler restores the rest in `deserialize()`.

- **Times are saved relative to `CL.time`** and re-anchored on load, as the particle system does. Save `die - CL.time`, not `die`.
- Build the value with `ClientSerialization.serialize()` (`source/shared/ClientSerialization.ts`). It supports numbers, strings, booleans, arrays, vectors and nested objects. Entity references and functions are deliberately not supported.
- On load the engine allocates the entity, restores its model, calls `spawn()` without parameters, restores origin, angles, velocity and the physics state, and then calls `deserialize()`. So `spawn()` may roll fresh random values or set a move type, and what was saved wins.
- Changing what a handler saves is a save-game format change for that handler. The engine's `gamestateVersion` guards the overall layout.

## Gravity particles

Particles are not client entities, there are far too many of them. The particle types that fall under gravity (`grav`, `slowgrav` and the explosion and blob particles) do collide with the world since this work: a floor-like impact bounces them with the shared clip formula, a wall or ceiling kills them. A cheap point classification gates the world trace, so open air costs next to nothing. `Particles.collidableParticleTypes` (`renderer/effects/Particles.ts`) lists which types take part.

## Registering handlers

The engine only calls `GetClientEdictHandler(classname)`. How a game answers is up to it. The `id1` module keeps its handlers in `client/entity/`, mirroring its server-side `entity/` folder, in a `ClientEdictHandlerRegistry` keyed by each handler's static `classname`: the client counterpart of its server `EntityRegistry`, with the same `precacheAll()` hook. It exports the list of its handler classes so a mod can spread it into its own registry. See the module's README for the mod-side example.

## Limits

- **Cosmetic only.** Client-only entities are not synchronized between players: every client rolls its own spin and lifetime. Anything that affects gameplay stays on the server.
- **No prediction or reconciliation.** There is nothing to correct against.
- **Timers keep running while the game is paused**, `CL.time` does not stop. The engine's physics does, so a gib hangs in the air until the pause ends.
- **`think()` is not culled.** Only drawing and `emit()` are. Many hundreds of expensive handlers add up.
- **World collision only.** `Traceline()` on the client traces the static world, not other entities.

## Examples in the `id1` game module

The `id1` module is the reference for how to use all of this. These are illustrations, not engine facts.

- **Gibs** (`client/entity/Gibs.ts`): a kill sends one event instead of spawning up to a dozen server edicts. The handler only picks `MOVETYPE_BOUNCE` and a random tumble, the engine does the flying, bouncing and coming to rest, and the handler removes the gib after 10 to 20 seconds. It is saved mid-flight.
- **Death bubbles** (`client/entity/Bubbles.ts`): one event releases a burst, each bubble hidden until its own delay has elapsed.
- **`air_bubbles`** (same file): the map entity makes itself static, and a client handler releases a bubble every second or two, only while it can be seen, and replays what it missed when it comes back into view.
